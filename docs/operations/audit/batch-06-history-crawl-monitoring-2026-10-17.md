## Findings — ZIP baseline / OPEN until current branch reconciliation
- **F39 P1 — Corrupt history silently omitted:** `history.py:120-147` `list` ignores invalid/unreadable assessment JSON; `prune` relies on this list (`history.py:155-164`) and cannot account for those hidden records. Reconcile retention and referenced reports before changing.
- **F40 P2 — History finding-signature semantics too broad:** `history.py:55-70,167-229` hashes the entire finding, including text fields. Editorial-only metadata changes appear as `changed`; assess intended semantics and separately track severity/status changes.
- **F41 P1 — No atomic link between monitoring assessment, usage ledger and notification:** `tenant_monitoring_execution.py:54-132` first saves assessment, then records reservation usage, then sends email. A ledger failure causes a job retry and another assessment; a late worker-success failure can repeat notifications. Need explicit idempotency keyed by job ID and stepwise durable status before modifying.
- **F42 P1 — Monitoring work can outlive lease:** `monitoring_worker.py:45-82` executes potentially long crawl/email using one fixed lease without heartbeat. A second worker may re-lease after expiry, duplicating effects. Confirm actual `SQLiteMonitoringJobStore.lease_next` policy; risk, not reproduced.
- **F43 P2 — Crawl resumed job relies only on saved assessment reference:** `tenant_crawl_execution.py:41-56` returns previously stored assessment and `job.pages_completed` without cross-checking recorded count; legitimate idempotency feature, but evidence mismatch could go undetected. Require invariant comparison before enabling revisions.
- **F44 P1 — Persisted project assessment lacks snapshot of all crawl inputs:** `tenant_crawl_execution.py:63-83` compares URL, profile name and max_pages with job but not all custom crawl limits. Modified depth/timeout/byte budget can change executed work without changing the validated triple. Compare full profile and limits fingerprint.
- **F45 P2 — Result reporting may hide notification failures:** `tenant_monitoring_execution.py:104-131` explicitly returns `EmailStatus.failed` without raising; `monitoring_worker.py:75-86` marks the overall job successful even when email delivery failed. Clarify contract of monitoring completion vs notification delivery; failures must remain visible and independently retryable.
- **F46 P2 — History directories require existence of current project:** `tenant_history_store.py:27-48` prevents access to assessments once a project JSON is deleted, while underlying evidence directory may persist. Good tenant authorization boundary, but needs recovery/migration handling before project deletion or archival.
