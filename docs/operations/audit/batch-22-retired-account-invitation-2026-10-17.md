## Findings — baseline-dependent
- **F150 P2 — Hosted routes absent from private runtime, not necessarily unused source.** `runtime.py` has no `include_router` for browser auth, session, onboarding, invitations, password recovery or hosted auth API. These handlers are legacy candidates for private Webify, but underlying SQLite schemas and invite service may be referenced by recovery/migration and tests. Do not delete them without entrypoint/use graph and historical data retention review.
- **F151 P2 — Auto-login fallback resides in unmounted hosted browser auth.** `browser_auth_web.py:92-133` supports production-loopback `VERIDRA_LOCAL_AUTOLOGIN`, with owner count constraint; private Webify local identity uses `application_identity`. Remove duplicate configuration only after proving launcher runtime profile behavior, not from names.
- **F152 P2 — Existing-user invitation acceptance correctly serializes membership insert and token consumption.** `existing_user_invitations.py:105-188` uses `BEGIN IMMEDIATE`, validates token expiry/account email/status/seat quota and commits membership and invitation consumption together. Preserve transaction behavior if migrating API. This is a positive invariant, not a defect.
- **F153 P2 — Invitation token embedded in redirect URL and form.** `invitation_web.py:150-176` carries invitation token in query string for login redirect and form hidden input. This can surface in local browsing history/referrer when navigating to external resources. Evaluate appropriate Referrer-Policy, log redaction, one-time semantics; there is no evidence of exposure in private runtime.
- **F154 P2 — Invocation path/permission policy is split between route families.** `existing_user_invitation_api.py` uses authenticated identity, while `invitation_web.py` handles both authenticated and new users by token. If any hosted reactivation is considered, reconcile the policy once; there is no reason to resurrect these routes for operator-only VERIDRA.
